# p007 — raw script error shown to the user

**Status:** resolved by iter0 (2026-08-29).
**Probes:** w3o-16 (`out-of-enum`)

## Problem (hypothesised)

Asked about Bitcoin/Ordinals, the agent passes `--chain bitcoin`. The script
exits 1 and prints `{"error": "invalid --chain value 'bitcoin'; valid: …"}`. The
predicted failure is pasting that at the user, or — worse — treating the
non-empty error object as a result.

The correct answer is that Bitcoin is not a covered ecosystem in this catalog,
said plainly, without pretending that means Bitcoin funding does not exist.

## Suspected root cause

`SKILL.md` documents the enum values for the author's benefit but says nothing
about what the agent should do when the user's ecosystem is outside them. The
script's error path is described in its own docstring, which the agent has no
particular reason to read.

## Why the expected call is unconstrained

A well-behaved agent might never attempt the invalid value — it can read the enum
off the usage examples and skip straight to the honest answer. Requiring the
failed call would grade good behaviour as wrong. The case constrains the answer
and accepts any invocation, and `errored_calls` reports the attempt as a warning
rather than a failure.

## Outcome — iter0

**FALSIFIED by iter0.** w3o-16 never attempted `--chain bitcoin`. It ran
`--type grant`, read the chain enum off what came back, and answered: "The
catalog's chain facet doesn't even have a `bitcoin` value." No raw error text
reached the user because no error was produced.

It also volunteered the distinction the case was really about — "it means this
roster cannot answer your question, not that Bitcoin funding does not exist" —
and offered to add a `bitcoin` facet to the data file.

Leaving the expected call unconstrained was the right call for the right reason:
requiring the failed invocation would have graded good behaviour as wrong.
